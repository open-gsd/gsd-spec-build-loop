# Wayfinder vs. gsd-loop

Research date: 2026-07-28

Sources were read at fixed revisions so the comparison remains reproducible:

- Matt Pocock `skills`: [`2ab9580`](https://github.com/mattpocock/skills/tree/2ab958093e83e0ec752e6c1c5932da465bf23e0c)
- `open-gsd/gsd-spec-build-loop`: [`e134fe3`](https://github.com/open-gsd/gsd-spec-build-loop/tree/e134fe3b954c9a75c44f8262b8648803e80bcd28)

## Bottom line

Wayfinder and gsd-loop solve adjacent phases, not the same problem. Wayfinder is an upstream discovery system for an effort that is both too large for one session and too foggy to specify: it turns unknowns into decision tickets and stops when the route is clear. It explicitly produces decisions rather than delivery artifacts. ([Wayfinder source](https://github.com/mattpocock/skills/blob/2ab958093e83e0ec752e6c1c5932da465bf23e0c/skills/engineering/wayfinder/SKILL.md#L7-L13)) gsd-loop is a downstream delivery system: it turns an idea into a contract-grade issue, turns an approved issue into a PR, and audits that PR before a human merge. ([gsd-loop README](https://github.com/open-gsd/gsd-spec-build-loop/blob/e134fe3b954c9a75c44f8262b8648803e80bcd28/README.md#L1-L36))

Matt's documentation is explicit about the handoff: Wayfinder sits upstream of `to-spec` and `to-tickets`; once the fog is gone, the normal flow resumes with `to-spec` (or direct implementation when the effort proves small). It is therefore not a full specification, build, review, or delivery loop. ([Wayfinder documentation](https://github.com/mattpocock/skills/blob/2ab958093e83e0ec752e6c1c5932da465bf23e0c/docs/engineering/wayfinder.md#L17-L21), [handoff](https://github.com/mattpocock/skills/blob/2ab958093e83e0ec752e6c1c5932da465bf23e0c/docs/engineering/wayfinder.md#L42-L44))

The clean composition is:

```text
large, foggy idea
  -> Wayfinder map
  -> resolved decision frontier
  -> gsd-loop spec issue(s)
  -> human gsd:ready
  -> gsd-loop build/review lanes
  -> human merge
```

## Strong similarities

Both workflows use the issue tracker as durable coordination state rather than trusting chat memory. Both claim work by assignment before deep work, make each session/pass bounded, represent dependencies explicitly, and stop instead of guessing when human judgment is required. ([Wayfinder](https://github.com/mattpocock/skills/blob/2ab958093e83e0ec752e6c1c5932da465bf23e0c/skills/engineering/wayfinder/SKILL.md#L55-L71), [gsd-loop](https://github.com/open-gsd/gsd-spec-build-loop/blob/e134fe3b954c9a75c44f8262b8648803e80bcd28/loop/build.md#L129-L151))

Both also make scope explicit, but at different resolutions. Wayfinder draws a destination, evolving fog, and an `Out of scope` boundary. gsd-loop converts the final scope into individually auditable `O-N` promises and `X-N` fences. ([Wayfinder](https://github.com/mattpocock/skills/blob/2ab958093e83e0ec752e6c1c5932da465bf23e0c/skills/engineering/wayfinder/SKILL.md#L82-L101), [gsd-loop](https://github.com/open-gsd/gsd-spec-build-loop/blob/e134fe3b954c9a75c44f8262b8648803e80bcd28/loop/spec.md#L61-L107))

## Where each is stronger

Wayfinder is stronger when premature ticket slicing would encode guesses. Its map can admit that part of the work is not yet specifiable, grow the decision graph as facts emerge, mix human conversations with prototypes and AFK research, and expose parallel decision work through the tracker frontier. ([source](https://github.com/mattpocock/skills/blob/2ab958093e83e0ec752e6c1c5932da465bf23e0c/skills/engineering/wayfinder/SKILL.md#L65-L91))

gsd-loop is stronger once implementation is authorized. Its contract binds both builder and reviewer, its builder reconstructs crashed state from Git and GitHub, and its review verdict is tied to an exact PR head and linked issue; new commits invalidate old approval evidence. ([contract](https://github.com/open-gsd/gsd-spec-build-loop/blob/e134fe3b954c9a75c44f8262b8648803e80bcd28/loop/build.md#L142-L161), [recovery](https://github.com/open-gsd/gsd-spec-build-loop/blob/e134fe3b954c9a75c44f8262b8648803e80bcd28/loop/build.md#L26-L53), [verdict identity](https://github.com/open-gsd/gsd-spec-build-loop/blob/e134fe3b954c9a75c44f8262b8648803e80bcd28/loop/review.md#L47-L72)) It also refuses approval without required CI and requires normalized baseline-versus-head security evidence when dependency files change. ([source](https://github.com/open-gsd/gsd-spec-build-loop/blob/e134fe3b954c9a75c44f8262b8648803e80bcd28/loop/review.md#L150-L212), [CI gate](https://github.com/open-gsd/gsd-spec-build-loop/blob/e134fe3b954c9a75c44f8262b8648803e80bcd28/loop/review.md#L226-L251))

## Recommended integration

Do not replace gsd-loop's spec contract with a Wayfinder map. A resolved Wayfinder decision ticket contains an answer, while a gsd-loop queue item additionally needs observable outcomes, binding exclusions, code pointers, test intent, a manual walkthrough, and a roughly one-agent-day scope. ([Wayfinder resolution](https://github.com/mattpocock/skills/blob/2ab958093e83e0ec752e6c1c5932da465bf23e0c/skills/engineering/wayfinder/SKILL.md#L118-L126), [gsd-loop issue contract](https://github.com/open-gsd/gsd-spec-build-loop/blob/e134fe3b954c9a75c44f8262b8648803e80bcd28/loop/spec.md#L61-L107))

Instead, add Wayfinder as an optional pre-spec lane:

1. Invoke Wayfinder only for a multi-session effort whose route is genuinely foggy; skip it when the change can already be specified. ([source](https://github.com/mattpocock/skills/blob/2ab958093e83e0ec752e6c1c5932da465bf23e0c/docs/engineering/wayfinder.md#L17-L21))
2. Resolve decision tickets until the map has no actionable fog before the destination; retain its decisions and out-of-scope calls as planning provenance. ([source](https://github.com/mattpocock/skills/blob/2ab958093e83e0ec752e6c1c5932da465bf23e0c/skills/engineering/wayfinder/SKILL.md#L82-L101))
3. Feed that resolved context into one or more `gsd-loop-spec` sessions. Translate decisions into `O-N` outcomes and Wayfinder scope boundaries into `X-N` exclusions, then add the code, test, and walkthrough evidence Wayfinder intentionally does not produce. ([source](https://github.com/open-gsd/gsd-spec-build-loop/blob/e134fe3b954c9a75c44f8262b8648803e80bcd28/loop/spec.md#L61-L107))
4. Keep the existing human `gsd:ready` gate, unattended build/review lanes, and human-only merge unchanged. ([source](https://github.com/open-gsd/gsd-spec-build-loop/blob/e134fe3b954c9a75c44f8262b8648803e80bcd28/README.md#L90-L98))

This gives gsd-loop a principled answer for work that is too uncertain to pass its current spec-closure test, without weakening the contract or the delivery safeguards once work enters the ready queue.
